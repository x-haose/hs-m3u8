# ADR-0006：HLS 播放列表解析自行实现

- 状态：已采纳
- 日期：2026-10-09

## 决定

`crates/hls` 自行实现播放列表的词法解析与规范化，不依赖第三方 m3u8 解析库。

原则：格式上的不规范一律容忍（BOM、CRLF、空白、属性名与枚举值大小写、值不加引号、IV 不带 `0x`、小数形式的 TARGETDURATION、超出 TARGETDURATION 的分片时长、未知标签）；影响语义的标签写坏时报错并给出行号，不静默丢弃。第一行必须是 `#EXTM3U`，用来拦住服务器返回的 HTML 错误页。

## 考虑过的方案（2026-10-09 实测）

crates.io 上按下载量的两个候选，用 15 组真实网站常见的写法对比：

| 写法 | m3u8-rs 6.0.1 | hls_m3u8 0.7.0 |
|---|---|---|
| 同一位置两个 EXT-X-KEY（identity + Widevine） | 只留最后一个，能用的 AES-128 key 丢失 | 两个都保留 |
| KEY 的 URI 未加引号 | 整个 key 被丢弃，分片被当成未加密 | 通过 |
| `#EXT-X-TARGETDURATION:10.0` | 解析出 3 个分片（实际 2 个），不报错 | 报错 |
| 分片时长超过 TARGETDURATION | 通过 | 报错 |
| IV 不带 `0x`、METHOD 小写 | 通过 | 报错 |
| BOM、缺少 `#EXTM3U` | 报错 | 报错 |

- m3u8-rs 会静默丢失或错算语义信息；每个分片只有一个 `key` 字段，时长用 `f32`。
- hls_m3u8 模型正确（分片可有多个 key），但对真实网站极常见的写法直接拒绝。

## 后果

- 自写解析器约 500 行，测试覆盖规范化规则与容错行为（行覆盖 91%）。
- 规范化规则（KEY 按 KEYFORMAT 跟踪、缺省 IV 取媒体序号、MAP 与 BYTERANGE 的作用范围）直接在本 crate 内实现，无需在第三方模型与本项目模型之间翻译。
